# Keyscape 项目协作说明

本文件记录项目方向、参考项目中的可借鉴经验，以及适合当前阶段的开发方式。后续工作以用户最新决定和实际代码为准；方案建议不能自动视为已确认需求。

## 最新方向：整体设计先成立，题材可以更换

- 用户再次强调：核心创意是以键盘为画布，场景不必限定为海域。
- 完整键盘必须能被立即辨认；标准错位行列、长空格和特殊键位比例优先建立，不能依赖文字解释其为键盘。
- 整体构图、视觉重心、轮廓和色彩关系需要先成立。单键精细程度不能代替整体审美验收。
- 用户进一步强调：键盘只是画布，画面内容和表达是主体。先确定作品的意境、视觉引导、主次与空间组织，再让行列、宽键、空格及边框参与表达；避免仅把键盘改成好看的材质或逐键摆放同主题装饰。细节疏密应服从画面，不能平均分配。
- 最新用户允许更大胆的想象，不让键盘局限作品。概念探索可突破完整外轮廓，让键位弯曲、悬浮、破开或延伸成空间；保留键盘作为表达起点与可发现的结构联系，不用早期“必须完整保留标准外形”的规则否决大胆方案。具体变形程度仍待视觉评审。
- 海域、山水地形等均是可探索题材，下面的海域规则属于该题材的既有方案，不得因此强制后续继续画海。
- 用户评价山水河谷方向“不带劲”，要求继续多方向尝试。最新探索包含雨夜街区、赤岩峡谷、雨林遗迹、月面基地、超现实花园、液态金属，均待评审，不能自行视为最终方向。
- 后续保留每键画布、整体画布、紧密衔接、特定艺术键全屏与旋转等核心体验，按具体题材调整资产和材质。

## 1. 项目目标与当前边界

- 暂定名称：Keyscape — Ocean Keys。
- 制作以键盘为画布的交互式 3D 艺术网页；海域、群岛和微缩地形是已探索方向，题材仍可调整。
- 最新核心要求同时包含两个尺度：整把键盘是一片完整海域，每个键又是其中一幅细节丰富、可独立放大旋转的局部作品。单键内容与整体连续性需要同时成立。
- 键盘是主要视觉主体，仍需保留整体比例、行列秩序和特殊尺寸按键的识别线索。
- 键帽顶部不显示字符；通过可辨认的键帽轮廓、材质和键位节奏表达结构。艺术键的厚度与立体地形以单键设计表现为准。
- 每颗键拥有自己的地形、水体或水下细节；相邻键的水色、海床、浅滩、岸线与岛群在视觉上连贯，共同组成一片具有统一地理构图的海域。不能把“单键画布”和“整片海域”当成二选一。
- 按键之间紧密粘连、近乎齐平，只保留低对比细缝与基本键位轮廓；避免独立玻璃方块、深黑缝和逐键发光描边。整把键盘也是统一画布，水面、岸线和海床应跨键自然延伸，内部键帽侧壁不应形成视觉分隔。
- 键盘外框也必须是海域画布的一部分：海水、海床、浅滩或礁岸延伸至外缘，避免一圈与主题割裂的白色塑料框或厚底座。
- 用户对上一轮反馈：相较完全弱化键位的第二张，更偏向第一张保留键位可读性的结构；保留基本行列和特殊键位，避免将其抹平成难以识别键盘的景观板。此前概念图的审美尚未获认可，不能作为已确认美术基准。
- 用户随后明确认可 V3 的蓝洞单键和渔港单键。后续以这两张的真实地形体积、水下纵深、建筑尺度和材质工艺作为美术参考；V4–V6 整体图未获认可，不能将其平面化表现当成基准。完整键盘仍需同时满足紧密连接、整体海域与单键细节。
- 默认视图聚焦一个完整键盘，强调设计感、3D 质感与沉浸感，页面保持简洁。
- 点击特定艺术按键后触发切换动画，被选中的单键放大为全屏展示主体；键盘与单键均支持旋转操作。
- 可以搭配天气、薄雾、水面等轻量动态和交互，效果应服务于主体，避免遮挡或争夺视觉中心。
- 首版不扩展真实打字、按压模拟、配置器、账号系统、复杂粒子玩法或无关信息面板。

以下仍是待验证建议，不得直接写成最终设计：

- ANSI 60%／61 键布局只是原型基线候选，最终布局尚未确定。
- 背景、艺术键数量与单键陆海比例均需围绕具体主题评审，不将先前整片海域方案的低陆地占比约束强加到每颗艺术键。
- 写实程度、水体透明度、接缝形式、底座造型及最终岛群分布仍需可运行原型验证。
- 单键全屏展示与旋转已由用户确认；具体过渡时长、对象变换与镜头运动的组合方式仍需原型验证，不再将局部岸线镜头特写视为该需求的完成。

## 2. 参考项目的使用原则

主要参考：<https://github.com/luoban25/resin-diorama-collection>。

- 借鉴场景分层、程序化资产、共享资源、水体渲染和性能控制的思路。
- Keyscape 建立一个统一应用，不复制原仓库三个独立作品的代码副本结构。
- 可借鉴原项目的完整微缩景观层次，将其组织为单颗艺术键。不同键位应具有自己的主题与构图，同时统一材质、尺度和细节语言。
- 程序化生成不等于随机构图：岛群、视觉重心和留白应由美术设计控制，种子随机数用于可复现的局部细节。
- 原仓库检查时未见 LICENSE。直接复用源码或资产前确认授权条件；参考思路与直接复制代码应区分。

## 3. 技术栈与模块职责

优先评估 Vite、React、TypeScript、Three.js、React Three Fiber 和 drei，使用经过实际安装与构建验证的兼容版本并提交锁文件。

建议职责划分：

- 应用界面：标题、简短说明、返回入口、加载和错误反馈。
- 场景编排：组织键盘、海床、岛群、水体、灯光与相机。
- 布局数据：键位标识、位置、尺寸和拾取范围。
- 海域数据：地形高度、水深、湿区、岸线和接缝信息。
- 图形模块：水面、透明外侧、程序化模型、材质和实例化工具。
- 交互模块：拾取、拖动判定、选中区域、聚焦与返回。
- 运行质量：画质档位、性能测量、资源加载和释放。

React 管理离散的界面与交互状态；逐帧模拟、相机更新和 shader 参数使用适当的引用及渲染循环，避免每帧触发 React 状态更新。

Leva 可用于开发调参，正式观赏页面默认隐藏。后处理和 GSAP 根据实际需要引入，不作为必需依赖。

## 4. 单键画布与整套一致性

- 每颗艺术键有独立局部坐标、主题、地形、水深、岸线、资产配置和内容边界。键盘坐标负责摆放这些艺术键。
- 同时保留整把键盘的海域构图与相邻关系。共享区域色彩和地理设计为单键提供衔接基准，局部细节按键组织；不把所有键变成重复蓝色方块，也不把一座巨型地形简单覆盖在整把键盘上。
- 单键内部的几何、水深和湿区共享数据源，避免岸线、遮罩和水体错位；可借鉴 `lunarGeometry.ts` 的数据一致性思路。
- 丰富细节分层组织：主要地标与轮廓、岸线和建筑、码头与小物、水下海床与生态。细节应形成前中后景和明确视觉主次。
- 建筑、植被、岩层、沙滩、船只和水下生态按单键主题组合，避免所有按键使用同一座灯塔、同一组岛屿或相同布局。
- 统一整套的光照、色彩关系、微缩比例和材质品质；将渔村港湾、礁岸、蓝洞、浅滩与深海按有意义的相邻关系排布，形成完整海域，而非任意拼放的独立收藏品。
- 整体观赏保持清晰的键位秩序；丰富细节在全屏单键状态得到充分展示，不要求整体视图同时绘制所有最高精度内容。
- 不以密集白色焦散、发光描边或重复装饰代替真实地形和生态细节。
- 在完整键盘构图中验证一到两颗精致代表键，同时检查近邻衔接与整体海域关系，再扩展细节。

## 5. 水体实现与移植注意事项

- 先验证静态颜色、海床深度、岸线和基础高光，再逐步增加折射、波纹传播与焦散。
- 首个原型可以使用简单动态法线或解析波纹；GPU 高度场模拟按验证结果引入。
- 单键水体可以独立表达。整体态优先共享兼容的渲染资源或使用低成本表面效果，避免所有键同时开启高成本模拟与多次场景捕获；单键态将预算集中给选中键。
- 模拟、表面渲染、透明侧壁和交互分开组织，便于单独调试和降级。
- 如采用原项目的双缓冲高度场思路，需要参数化各艺术键的水域尺寸、坐标映射、湿区和边界。
- 对宽键和不同形状的水域，分别处理网格间距、传播计算、法线梯度和稳定步长，不能只拉伸平面。
- 高度场适合表面波纹，不将其描述为完整三维流体或 SPH。
- 透明、折射和焦散是为艺术表达服务的视觉近似，不追求未经验证的物理真实性。
- 相机或整体物体变换时，水纹应保持与键盘坐标一致，避免滑动或缩放失真。
- 离屏渲染时排除水体自身，并恢复被修改的渲染目标、可见性和渲染器状态。

## 6. 拾取、单键全屏展示与旋转

- 为特定艺术键配置明确的标识、拾取范围、展示模型和内容边界。点击后，该键成为页面中唯一的主要展示对象，整体键盘在过渡后退出主体画面。
- 将视觉表面与拾取逻辑分开，避免依赖复杂透明材质本身确定选中键位。
- 原项目水面事件中的 `stopPropagation()` 不能不加分析地照搬，否则可能阻止下层键位接收事件。
- 明确区分拖动和点击，避免旋转结束后误触发聚焦。
- 相机由一套控制系统统一管理；不要让控制器和动画库同时持续写入相机。
- 可优先评估 drei 的 CameraControls。GSAP 可按需承担界面或其他动画，不必重复承担同一镜头控制职责。
- 使用明确的状态：整体键盘、选中与抬升过渡、单键全屏、返回过渡。
- 整体态旋转完整键盘；单键态围绕独立艺术键观看各侧面。首版可通过受控镜头环绕实现观赏旋转，避免相机和模型同时响应同一手势。
- 切换可结合选中反馈、轻微抬升、背景退场、平滑放大和重新构图；整段保持同一艺术键的视觉身份，不使用无关联图片硬切。
- 切换前保存整体视角，返回时恢复位置和视角；处理快速连续选择、过渡中返回、窗口尺寸变化和触屏操作。
- 整体态与单键态使用同一艺术键的配置、种子、材质和局部水域坐标；近景增加精度时避免主体形态和水纹跳变。
- 全屏展示保留极简返回入口和必要操作提示。天气与背景动态退居辅助，不在该状态继续展示大面积键盘或并列详情面板。

## 7. 资产、性能与资源管理

- 普通键位、岩石和植物优先共享几何体与材质，同构重复物件按合适批次实例化。
- 实例化不能消除阴影、透明和离屏渲染的成本；同时关注渲染通道和像素开销。
- 少量核心艺术区域可以使用独立模型，统一尺度、材质粗糙度、颜色和细节密度。
- 精细内容按观察距离和选中区域加载；整体视图保留稳定的低精度形态。
- 避免在首屏同步生成大量高分辨率纹理或高面数几何，必要时预生成、缓存或分阶段处理。
- 控制像素比、阴影、折射分辨率和后处理，整体视图优先保持清晰与稳定。
- 自适应画质以实测性能为依据，避免只用 CPU 核心数判断 GPU 能力；如支持恢复画质，使用足够的观察窗口和迟滞避免反复切换。
- 页面隐藏时减少或停止更新；静态／暂停模式应检查是否仍在执行无必要的离屏渲染。
- 释放不再使用的纹理、材质、几何体、渲染目标、事件监听和异步任务。
- 记录外部字体、环境图和模型来源；提供加载失败回退，评估将必要资源随项目托管。
- 尊重减少动态效果设置，必要时提供静态展示回退。

桌面 60fps、低档 30fps 可作为初始目标，须记录设备、视口、像素比和画质后测量。构建成功或首屏出现不等于性能与兼容性验证完成。

## 8. 借鉴 BMAD 的推进方式

参考：<https://github.com/bmad-code-org/BMAD-METHOD>。

采用其显式决策、持久上下文、按工作规模规划和小步验收的原则。当前不将安装完整框架、多角色流程或长篇 PRD 作为开始原型的前置条件。

- 复用已有设计概要，区分已确认要求、待验证假设与首版范围，避免重复生成内容相同的文档。
- 先验证风险最高的视觉与技术假设，再固化架构；不要把未验证的美术参数过早写成不可变需求。
- 每次任务明确目标、边界、依赖和验收方式，以可观察成果结束。
- 保留关键技术选择及理由；原型推翻某项选择时同步更新记录。
- 根据已有授权持续推进；需要用户判断时，提供具体画面、操作或测量结果作为讨论依据。
- 若后续开发跨度、团队协作或任务追踪复杂度增加，再评估正式安装 BMAD 工具链。
- 真正安装时重新核实当前稳定版本、对应文档与环境要求，并固定所用版本，不混用不同版本的工作流。

项目记录保持精简：项目说明、架构决策、任务与验收清单。规模尚小时允许合并，避免为文档数量而拆分。截图与运行结果作为视觉决策的证据。

## 9. 推荐实施顺序与验收

1. 双尺度构图：用完整低模键盘建立统一海域，并放入代表艺术键，检查整体辨识度、海域连贯性和单键画布是否同时成立。
2. 代表键细化：验证单键轮廓、地形、岸线、水下层次和材质，确保全屏观赏有足够内容，同时保持近邻衔接及细节分级。
3. 观赏交互：完成特定艺术键拾取、过渡、单键全屏、独立旋转与返回。检查快速切换、误触、尺寸变化和触屏。
4. 代表性艺术内容：扩展少量重点区域，统一比例、材质和构图留白。
5. 水体与性能：按需要增加 GPU 波纹、折射和焦散，测量后决定画质预算与降级方式。
6. 发布验证：完成生产构建、资源加载、错误回退及目标浏览器检查。

优先交付的原型：一片由完整低模键盘组成的海域＋代表键的完整细节＋单键全屏切换与旋转。整体是连贯海域，每键是局部画布，两项共同验收。

验证时区分：

- 逻辑正确性：布局映射、拾取身份、坐标转换和相机状态。
- 视觉表现：固定视角与尺寸截图、单键细节层次、整体键盘辨识度、两种状态的身份一致性和不同画质对比。
- 运行质量：首屏、旋转、聚焦、局部加载时的帧耗时，以及资源重复加载与释放。

仅在能有效验证行为或风险时编写测试，避免镜像实现的测试和无依据的重复检查。汇报时明确区分已完成验证、设计建议和未实测假设。
