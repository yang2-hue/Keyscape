# 月湾环抱 · 产品验收记录（v11）

日期：2026-10-26
对象：当前代码（单作品展厅 · 五个时刻自动轮播 · 三个交互点 · 船两次点击复位）
依据：`docs/crescent-product-acceptance.md` 的 5 项整改要求与通过标准
性质：**实际运行截图、录屏与数值断言**，不是概念图，也不是真机性能报告

## 结论

5 项要求中，**3 项通过**（岛与码头过渡、灯塔入口、夜间灯塔工作表现），**2 项基本通过但视觉可读性仍偏弱**（可用平地、小屋入户通路的铺装辨识度）。

仍需你判断的是两件美术层面的事：夜间扫海光束的亮度、门前铺装与挡土墙顶的对比度。这两项我没有擅自改参数。

## 怎么复核

```bash
./node_modules/.bin/vite --host 127.0.0.1 --port 5173 --strictPort   # 终端 A
node scripts/crescent-acceptance.mjs                                  # 终端 B，约 5 分钟
```

脚本会重新生成同目录下的 6 张截图、1 段录屏与 `check.json`，11 项断言全过才返回 0。视角由 DEV 专用的 `window.__galleryCamera` 直接取景，不依赖鼠标拖拽，因此每次跑出来的构图一致。

**注意**：展厅现在按 5 个时刻自动轮播（20 秒一步：早上晴 → 早上雨 → 晚上晴 → 晚雾 → 晚上雨），所以脚本开头用 DEV 专用的 `window.__galleryCycle.set(0)` 冻结在“早上晴”，夜景区段再 `set(2)` 切到“晚上晴”。生产包不含这些句柄。

## 逐项对照

### 1. 岛与码头缺乏合理过渡 — 通过

| 项 | 结果 |
| --- | --- |
| 平台高度 | 岸上平台 `TERRACE = 0.43`，码头平台 `LANDING.y = 0.13`，栈桥面 `0.13`（水面 0.08） |
| 总高差 / 级数 | 0.300，**23 级**，级高随长度均分而不是照抄地形 |
| 级高 / 踏面 | 最大级高 **0.0167**，最小踏面 **0.0265**（人尺度参照：小屋门高 0.165） |
| 接入地形 | 地形在同一组折线上下挖 `y - 0.028`，台阶不会悬空或埋入 |
| 栈桥落地 | 栈桥起点落在岸边平台上，`pier-posts` 从 `crescentHeight` 起算到桥面，有真实支撑 |
| 登船位 | `BERTH = (0.10, −0.22)`，与栈桥 T 形平台端头对应，泊船就停在平台侧 |

证据：`dock-view.png`（岸阶—栈桥 T 形平台—系缆桩—泊船的连续关系）、`aerial-view.png`（整条动线一次读完）。
测试：`shore stairway descends continuously and lands at dock height`（连续性、末级高度、级高上限、踏面下限）。

### 2. 岛屿可用平地不足 — 基本通过

| 项 | 结果 |
| --- | --- |
| 台地范围 | 半径 0.79–1.38 的环形带被整平到 `TERRACE = 0.43`，覆盖主路、两栋小屋与灯塔 |
| 小屋地基 | 基座按四个角点的**最高**地形取值，不悬空不下沉 |
| 门前地面 | 门前点实测高度 **0.4300**，与台地齐平 |
| 主路 | 100 个采样点全部位于 `0.43 − 0.06 … 0.43 + 0.006`，且高出水面 0.2 以上 |
| 道路宽度 | 铺装 0.13 宽，两栋小屋中心间距约 1.1，店前留白够站人 |

证据：`aerial-view.png`、`cottage-view.png`。
测试：`main walking route has dry ground without intervening terrain spikes`、`every cottage has an inward entrance connected to the main road`。

**未完全达标的地方**：台地在视觉上就是"挡土墙顶那一条弧带"，小屋门几乎贴着弧带外沿，读起来像"门开在崖边"——虽然数值上门前就是主路。要让"门前平台"更明确，需要把小屋向外挪 0.03–0.05 或把台地内缘再放宽，属于形体调整，等你定。

### 3. 小屋缺少完整入户通路 — 基本通过

- 两栋小屋各有一条 `HOUSE_PATHS` 支路：从主路（r=0.94）沿径向铺到门前（r≈0.995），**支路终点就是门口点**，不是"消失在附近"。
- 门口石块、门槛、门前台阶（两级）都在几何里，门朝岛内（`ry = atan2(−cos a, −sin a)`）。
- 道路范围内的岩石、植被由 `keepAccessClear` 剔除（沿路线 0.075 内 + 小屋周围 0.24 内不种）。

证据：`cottage-view.png`、`aerial-view.png`。

**未完全达标的地方**：支路铺装与挡土墙顶用的是同色石砖（`#e7dfc9` / `#cfc7b5`），在这个距离下两者几乎融合，"支路"读不出来。建议把支路换成更深的色阶或加一道边石——同样是等你确认的美术决定。

### 4. 灯塔缺少入口与通路 — 通过

| 项 | 结果 |
| --- | --- |
| 支路 | 主路 → `islandPoint(TOWER.a, 0.94)` → 塔门铺装，塔门实测离主路 < 0.06 |
| 塔门位置 | 世界坐标 `(0.308, 0.551, 1.148)`，落在塔院圆盘内 |
| 塔院 | `LighthouseCourt` 半径 0.17–0.18，高出地面 0.045，塔身半径 0.10，落脚面宽裕 |
| 门朝向 | 朝向向量与"指向岛心"的点积 **> 0.9**，不开向悬崖或水面 |
| 门槛 | `threshold` 砖 + 门前铺装，外部入口与塔体对应 |

证据：`tower-view.png`（塔门、塔院、右侧弧形铺装与主路的衔接一次读完）。
测试：`the lighthouse door is reachable from the main road and faces inland`（本轮新增）。

**护栏**：塔院临崖处本轮没有做矮墙。验收文件写的是"根据风险和视觉需要设置"，我判断当前尺度下强制加反而挡视线，列在这里等你选。

### 5. 夜间灯塔缺少明确工作表现 — 通过

| 要求 | 实测 |
| --- | --- |
| 可见灯室光源 | 夜航时灯球 `emissiveIntensity 1.6` + 光晕 sprite（`opacity ≈ 0.55`）+ 点光源 `1.35`，`beaconStrength 0.94`；白天三者全为 0，灯室是深色玻璃 |
| 缓慢旋转的扫海光束 | `0.24 rad/s`，**26 秒一圈**；12 秒录屏实测转过 **104°**（203 帧，见下文重定时说明） |
| 方向连续、不穿塔体屋顶 | 光束挂在 beacon 组内、灯室高度 `y ≈ 1.25` 水平射出，锥体在屋顶（`1.38`）之下、塔身（`≤1.10`）之上 |
| 夜间压低环境光 | `environmentIntensity 0.12`、环境光 0.14、太阳 0.18，灯塔成为焦点 |
| 暂停冻结 | 暂停后 `beaconAngle` 前后两次读值完全相同（`−0.682`），鱼尾与船体时间也冻结 |
| 减少动态 | 静止模式 `beaconAngle` 不变（`−0.608`），同时 `beaconStrength 1.0`——静态照明保留 |
| 日夜切换平滑 | 强度走 `damp(…, 3, dt)`；暂停时切换仍有过渡帧（见 `gallery-verify-v09` 的同名断言） |

证据：`night-view.png`、`reduced-motion.png`、`lighthouse-sweep.webm`（12 秒，900×700，VP9）。

**未完全达标的地方**：光锥片元是最简单的 `strength × 0.10 × fade` 加色混合，默认观察距离下能看到，但**偏弱**；夜景里道路与岸线的辨识度也偏低。要更"扫海"，把 0.10 提到 0.16–0.2 并给光锥加一点体积感即可，但这是美术决定，我没有动。

**新增（本轮）**：白天点一下灯塔，灯室会闪三下（`flash` 3.6 秒）并让光锥以 0.95 rad/s 加速扫过——这是验证"白天确实不亮"最直接的方式：不点它，它就是暗的。

## 录屏说明（重要）

`lighthouse-sweep.webm` 是**真实运行的连续帧**，但有一个必须说明的重定时：

- 无头 Chrome 用 SwiftShader 软件渲染，本机只有 **≈2 fps**；水波求解器每帧最多推进 6 × 1/120 秒，所以**场景时间只有墙钟的十分之一**。
- 直接录 12 秒墙钟，光束只会转 13°，看不出在扫。
- 因此脚本录 **119 秒墙钟**，本次得到 **203 帧**，再按实际帧数重定时压到 **12 秒**。

本轮重定时后光束转过 104°（上一轮 93°），差异来自捕获帧数，场景里的角速度没有变：`0.24 rad/s`。

所以：画面内容是真实的，扫光速度也是真实的，但**帧的节奏反映的是捕获率，不是真机表现**。真机上这段应该是流畅的 12 秒。

顺带记录一个环境坑：Playwright 自带的 `recordVideo` 在本机静默失败——它 spawn 的 ffmpeg 只编进了 `libvpx-vp9`，却请求 `-c:v vp8`，于是 `Unknown encoder 'vp8'` 且不落盘。脚本改为用 CDP `Page.startScreencast` 抓帧、再调同一个 ffmpeg 的 `image2pipe` 输入合成。

## 性能

**本次没有做真机性能结论。** 上面的 2 fps 是软件渲染，不能代表硬件。需要你在自己的手机/笔记本上跑一次，模板见 `docs/`（若无，可用开发者工具的 Performance 面板记录 10 秒，关注帧时间与 GPU 占用）。
